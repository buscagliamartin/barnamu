# BarnaMu — W Coin Economy & Auction House — Implementation Plan

> Status: **DESIGN COMPLETE — not yet implemented.** This document is the full,
> step-by-step build plan. Pick it up in a future session and implement phase by phase.
> Roadmap position: this is the W Coin / Auction House tier. Remaining tiers after it:
> PvP Duel Ladder, then the Live Admin Board.

---

## 1. Locked decisions

| Topic | Decision |
|---|---|
| Item escrow | **Real DB escrow** — the actual `Item` entity is moved into a server-owned storage and handed over intact. Full fidelity for any gear (level, excellent/luck/skill/ancient options, sockets, durability). |
| Currencies | **Zen, W Coin, Jewels.** Seller picks the price *amount* and *currency*. Jewel pricing uses one of the jewel-bank types. |
| Jewel payment source (buyer) | Buyer may pay jewels **from the jewel bank or from inventory**. |
| Jewel payout (seller) | Seller receives jewels **into their jewel bank**. |
| W Coin earning | **GM command + web top-up** (BarnaMuWeb). |
| Auction House UI | **Custom client window that replaces the personal store entirely.** |

- `CashShopPacketSender.SendPointInfoAsync(double wCoinC, double wCoinP, double goblinPoints, double mileage)`
  already exists and writes the point packet — we just need to feed it a real number.
- Conclusion: the W Coin economy is **greenfield**.

### 2.2 The found plugin — `C:\MuDev\AuctionHousePlugIn.cs`
- Class `JewelAuctionHousePlugIn : IChatCommandPlugIn`, key `/ah`.
- NOT in the compiled source tree (sits at the MuDev root) — it is **reference only**.
- JSON-backed (`jewel_auction_house.json`), jewels-only, Zen-only.
- Flow worth reusing: `sell` (item leaves bag) → `Listing`; `buy` (Zen deducted) →
  `PendingPayment` for the seller + `PendingPurchase` mailbox for the buyer;
  `claim` (seller collects Zen) / `receive` (buyer collects item). Offline-safe,
  scam-guarded (must retype type+price), ID recycling, `SemaphoreSlim` lock.
- **Fatal flaw for "all items":** it recreates items from `(Group, Number)` only via
  `CreateNew<Item>()` + `Definition` + `Durability`. Fine for fungible jewels;
  it destroys all gear value (level/options/sockets lost). This is exactly why we
  chose real DB escrow.
- **Use it as a structural reference for the flows; replace its persistence and item model.**

### 2.3 Codebase gotchas (learned this session — save time later)
- **EF migrations**: hand-written `.cs` files. Pattern = `C:\MuDev\OpenMU\src\Persistence\EntityFramework\Migrations\20260515120000_AddAccountVipExpirationDate.cs`
  (block-namespace, `[DbContext(typeof(EntityDataContext))]` + `[Migration("...")]` attributes,
  `Up`/`Down`). Also add the new columns to `EntityDataContextModelSnapshot.cs` (Account block,
  alphabetical). The server applies migrations automatically on startup.
- **Adding a scalar column to a DataModel entity** (e.g. `Account.WCoin`): edit ONLY the entity
  in `src\DataModel\Entities\`, the migration, and the snapshot. The EF model
  (`Persistence\EntityFramework\Model\*.Generated.cs`) and BasicModel are regenerated by a
  Roslyn source generator at build — do not hand-edit them.
- **Client packet files are XSL-generated and regenerated every build** — never hand-edit:
  `MuMain\src\source\Dotnet\PacketFunctions_ClientToServer.{h,cpp}`,
  `PacketBindings_ClientToServer.h`,
  `MuMain\ClientLibrary\ConnectionManager.ClientToServerFunctions.cs`.
  Custom client→server packets go in the hand-maintained extension files:
  `MuMain\src\source\Dotnet\PacketFunctions_Custom.{h,cpp}` (class `PacketFunctions_ClientToServer_Custom`,
  which the generated `PacketFunctions_ClientToServer` inherits) and
  `MuMain\ClientLibrary\ConnectionManager.ClientToServer.Custom.cs`
  (`[UnmanagedCallersOnly(EntryPoint = "ConnectionManager_Xxx")]`). The `.cpp` declares its own
  `typedef` + `inline dotnet_Xxx = symLoad(...)` — see `SendLogin` for the exact template.
- **Server→Client packets** (hand-written): receive dispatch is in
  `MuMain\src\source\Network\Server\WSclient.cpp`. Custom packets currently piggyback on the
  0xBF group with new sub-codes (jewel bank used 0xBF/0x30). The Auction House warrants its
  own main code — confirm a free one against the handler `Key`s.
- **Client UI windows**: registered via an `INTERFACE_*` id in
  `MuMain\src\source\Core\Globals\_enum.h`, created in `NewUISystem.cpp`, exposed via a getter
  + `g_pNewUIXxx` macro in `NewUISystem.h`. New `.cpp/.h` files must be added to the CMake/VS
  project; appending classes to an already-compiled file avoids that.
- **Builds**: server = `C:\MuDev\Bat\Recompilar.bat`; client = `C:\MuDev\Bat\Deploy Cliente.bat`
  (now robocopies the whole Release folder, so `MUnique.Client.Library.dll` ships with `Main.exe`).
- **Jewel bank**: the per-account bank already built has **17 slots** — `Account.JewelBank*`
  columns (`Bless, Soul, Life, Creation, Guardian, Gemstone, Harmony, Chaos, LowerRefineStone,
  HigherRefineStone, Kundun1-5, ChocoBlue, ChocoPink`). Jewel-currency pricing and jewel payouts
  reuse these columns.

## 3. Architecture overview

Two parts, built in order:

- **Part A — W Coin foundation (Phases 1–2):** a per-account W Coin balance + an audit ledger
  + ways to grant it (GM command, web). Must exist before the Auction House can price in W Coin.
- **Part B — Auction House (Phases 3–5):** server-side global market with real item escrow,
  three currencies, offline-safe mailbox, and a custom client window replacing the personal store.

---

## 4. Data model

### 4.1 W Coin
- **`Account.WCoin`** — `long`, NOT NULL, default `0`. The authoritative balance.
- **Ledger** — append-only flat file, one file per UTC day:
  `C:\MuDev\Logs\WCoin\YYYY-MM-DD.log` (env override `BARNAMU_WCOIN_DIR`, same pattern as
  `ItemAuditLogger`). Line format: `UTC timestamp | account login | delta (+/-) | balanceAfter |
  reason | note`. Reasons: `GmGrant, WebTopUp, AuctionSale, AuctionPurchase, AuctionRefund, AuctionFee`.
  - Rationale for flat file over a DB table: OpenMU's persistence is aggregate-rooted and has no
    precedent for a standalone unbounded log table; the flat file matches the proven
    `ItemAuditLogger`, and `Account.WCoin` remains the single transactional source of truth.
    (A real `WCoinTransaction` table is the alternative if web-side querying of history is
    later required.)

### 4.2 Auction House
- **Escrowed items → real DB storage.** A single server-owned `ItemStorage` ("auction vault").
  Listing an item moves the actual `Item` row into it; the item is never copied or rebuilt.
  *Open implementation question (resolve at Phase 3 start):* how to root a server-owned
  `ItemStorage` in OpenMU's persistence (candidates: a dedicated `ItemStorage` referenced by a
  fixed well-known Guid created on first run; or attach it to a system/template account).
- **Listing / delivery / payout metadata → JSON file** (`auction_house.json`, same survives-crashes
  approach the found plugin uses), each record referencing its escrowed `Item` by `Guid`.
  - `Listing`: id, sellerCharacterId, sellerName, itemId (Guid), itemDisplayName, price (long),
    currency (`Zen|WCoin|Jewel`), jewelSlot (0–16, only when currency=Jewel), createdUtc, expiresUtc.
  - `Delivery` (bought, awaiting buyer pickup): id, buyerCharacterId, itemId (Guid), price,
    currency, jewelSlot, sellerName, soldUtc.
  - `Payout` (currency owed to a seller): id, sellerCharacterId, amount (long), currency,
    jewelSlot, buyerName, soldUtc.
  - On load, reconcile JSON against the escrow storage (drop records whose item Guid is missing).
  - (Alternative: real EF tables — heavier; only if JSON proves insufficient.)

## 5. Phase 1 — W Coin foundation (server)

1. **`Account.WCoin` column.**
   - Edit `src\DataModel\Entities\Account.cs`: add `public long WCoin { get; set; }` with XML doc.
   - New migration `Migrations\<timestamp>_AddWCoin.cs`: `AddColumn<long>("WCoin", schema "data",
     table "Account", type "bigint", nullable false, defaultValue 0L)`; `Down` drops it.
   - `EntityDataContextModelSnapshot.cs`: add `b.Property<long>("WCoin").HasColumnType("bigint");`
     to the Account entity block (alphabetical).
2. **`WCoinService`** (new, `src\GameLogic\WCoinService.cs`): static helper.
   - `bool TryDebit(Player, long amount, reason, note)` — fails if balance < amount; else
     `Account.WCoin -= amount`, append ledger line.
   - `void Credit(Player, long amount, reason, note)` — `Account.WCoin += amount`, append ledger line.
   - Overloads taking an `Account` (for offline accounts, used by claims).
   - All ledger writes wrapped in try/catch (never throw); directory created eagerly.
3. **`/wcoin` GM chat command** (new plugin, `src\GameLogic\PlugIns\ChatCommands\WCoinChatCommandPlugIn.cs`).
   - `IChatCommandPlugIn`, `MinCharacterStatusRequirement = GameMaster`.
   - `/wcoin <player> <amount>` — grant (accept negative to remove); `/wcoin <player>` — query.
   - Resolve the target player; if offline, load the account, update, save.
4. **X-shop balance display.** Edit `CashShopPointInfoRequestHandlerPlugIn.cs`:
   replace `SendPointInfoAsync(0, 0, 0, 0)` with `SendPointInfoAsync(player.Account?.WCoin ?? 0, 0, 0, 0)`
   (W Coin sent as the "C" bucket; C/P split deferred).
5. **Verify**: build server (`Recompilar.bat`), `/wcoin` self, press X, confirm the balance shows.

## 7. Phase 3 — Auction House server core

1. **Resolve the escrow-storage rooting question** (see §4.2) — create the server-owned
   `ItemStorage` for escrowed items.
2. **`AuctionService`** (new, `src\GameLogic\Auction\`): JSON-backed, `SemaphoreSlim`-locked,
   loads on construction. Operations:
   - `List(player, inventorySlot, price, currency, jewelSlot?)` — validate; move the `Item`
     from the player's inventory into escrow storage; create a `Listing`. Enforce the
     per-character listing cap.
   - `Browse(filter)` — return listings, filterable by item type / currency, cheapest first, paged.
   - `Buy(player, listingId)` — validate; **debit the buyer**:
     - Zen → `player.TryRemoveMoney`.
     - W Coin → `WCoinService.TryDebit`.
     - Jewel → consume `price` jewels of `jewelSlot`: take from the jewel-bank balance first,
       then from inventory jewel items if the bank is short.
     - Move the escrowed item from escrow → a `Delivery` record for the buyer.
     - Create a `Payout` record for the seller (apply the sales-tax cut here).
   - `Cancel(player, listingId)` — seller only; move the item from escrow back to the seller
     (or to their delivery mailbox if inventory is full).
   - `ClaimPayout(player, payoutId)` — pay the seller: Zen/W Coin to balance, Jewel into the
     jewel bank.
   - `CollectDelivery(player, deliveryId)` — move the bought item from escrow into the buyer's
     inventory (refuse if no free slot — never lose the item).
   - `ExpireListings()` — periodic: listings past `expiresUtc` → item returned to seller's
     delivery mailbox; listing removed.
3. **Temporary `/ah` chat commands** wrapping `AuctionService` (extend the found plugin's command
   set) so the whole economy is testable before any client work.
4. **Verify** each currency path end to end via chat commands, including offline seller/buyer.

## 8. Phase 4 — Auction House client (replaces the personal store)

1. **Protocol** — a new custom packet group (own main code; confirm it is unused). Client→server:
   open, browse/filter, list-item, buy, cancel, claim-payout, collect-delivery. Server→client:
   listing page, my-listings, mailbox (deliveries + payouts), result/error messages,
   balance update (Zen / W Coin / jewel counts).
   - Client send side → `PacketFunctions_Custom.{h,cpp}` + `ConnectionManager.ClientToServer.Custom.cs`
     (see §2.3 — never the generated files).
   - Client receive side → `WSclient.cpp` dispatch.
2. **New client window** `CNewUIAuctionHouse` — tabbed: **Browse** (filter + listing rows + Buy),
   **Sell** (pick inventory item, set amount + currency, confirm), **My Listings** (cancel),
   **Mailbox** (collect bought items, claim payouts). Register in `_enum.h` (`INTERFACE_AUCTIONHOUSE`),
   `NewUISystem.{h,cpp}`.
3. **Retire the personal store**: redirect its entry point (key/menu button) to open
   `CNewUIAuctionHouse`; remove/disable the old personal-store window and its packet handling.
4. **Verify**: build client (`Deploy Cliente.bat`), full end-to-end test with two accounts.
5. Update the **MuHelper/Client ChangeLog** (`C:\MuDev\MuMain\MuHelper ChangeLog.md`) when done.

## 9. Phase 5 — polish

- **Sales tax** — default **5%** of the sale price, deducted from the seller's payout
  (a Zen / W Coin / jewel sink — healthy for a slow server). Make it a constant.
- **Listing expiry** — default **7 days**, then auto-return to the seller's mailbox
  (`AuctionService.ExpireListings`, run from a periodic task plugin).
- **Per-character listing cap** — default **10** active listings.
- Make all three tunable from one place.

## 10. Currency handling reference

| Currency | Buyer pays from | Seller receives into | Notes |
|---|---|---|---|
| Zen | `player.Money` | Zen balance (on claim) | `int` range; cap 2,000,000,000. |
| W Coin | `Account.WCoin` via `WCoinService` | `Account.WCoin` via `WCoinService` (on claim) | every move writes a ledger line. |
| Jewel | jewel-bank balance first, then inventory jewel items | jewel bank (on claim) | `jewelSlot` 0–16 = the 17 jewel-bank types. |

Sales tax applies to the seller's payout regardless of currency.
